# 七阶段分析插件 | 运行与验收手册

这是一份随源码交付的合并后手册。部署人完成 DeepSeek 合并后，按以下流程填入本机实际结果。

## 1. 准备

| 配置 | 值 |
| --- | --- |
| DSH_SEVEN_STAGE_STATE_DIR | 独立的绝对路径，部署给宿主和 Python 工具使用。不同 DSH 进程分别设置。 |
| DSH_SEVEN_STAGE_WORKFLOW_FILE | 当前 profile 的权威 workflow_state.json 绝对路径。由 _store.state_dir() 和现有状态保存函数定位。 |
| ~~DSH_SEVEN_STAGE_BRAVE_KEY~~ | **已废弃**（2026-11-18）。插件不再自己联网，不需要任何搜索密钥。检索由知识发工单、真实主对话用宿主内置 `web_search` 执行后 `search_fill` 回填。 |
| workerProvider（插件配置） | 默认 fork。安装的宿主支持原生 fork、第二层会话和独立的角色绑定。改用 spawn 前确认工作会话仍加载同一工具和限制。 |

目录创建后限制模型工具访问。重启合并后的隔离 profile，确认工程模式可进入，插件工具可见，普通模式及建模阶段照原设定加载。Windows 支持与项目当前的 Node 22 及以上宿主保持一致。

## 2. 在真实 DSH 中运行

1. **真实主对话**按工程模式原有入口建立任务、选范围并取得 taskId。用原生 subagent_fork 创建一级「总计子代理」。初始提示让它等待七阶段 attach 通知并使用插件工具，其他初始工作留给接入后再做。核对这是真实直系子会话。
2. **真实主对话**调用 engineering_seven_stage，action=attach，另传 taskId 和 dataJson 内容 {"planner":"一级子代理的真实 sessionId","messageIds":["原始需求消息ID"]}。省略 messageIds 时捕获最近一条真人原文。多轮输入时指定原始需求消息，避免误把最后一句模式确认当需求。
3. **总计子代理**收到接入通知，调用 action=launch。插件启动并预约三个二级会话。每个工作代理从原生启动消息取得角色、任务 ID 和一次性邀请码，第一次调用 action=bind。只有三个真实会话全绑定，才开始 1.1。
4. **总计子代理**逐步查看 action=status。按返回的 stepContract 和 actionHelp 组织当前决定，提交 frame，包含对象、当前决策、范围、搜索主题、复核方案与依赖。知识子代理从 status 取得 jobId，使用公开通用检索词调用 search。插件经 HTTPS 联网，记查询、时间、结果及来源 ID。知识用当前 job 的来源提交适用范围、具体出处和缺口。切勿把工厂专有名称、图纸、订单或完整需求放进搜索词；用不含专有数据的机理和公开型号检索。
5. **设计与反驳**按插件安排工作。1.1 先盲审原始需求，再给设计发布任务。之后按步骤依次提交设计与独立反驳。反驳必须说明对象、当前版本、遭违反的要求、机制、依据、影响、补证、负责人和关闭标准。一次争议达到两轮返工上限后转入 evidence_wait。关掉阻塞异议必须在复审中写逐项关闭依据。想回更早节点用 rewind；回退后下游消息凭据作废，并保留历史。
6. **真人缺口**经插件 question 转到真实根对话。真实根给用户展示当前决定、所需信息、原因和不知道时的取得办法，可用 yield 暂停。用户答后真实根通过 capture 采集该条原话和 ID，真值来自宿主消息。随后总计用 interpret 分类并给出冲突、参数和受影响的最早步骤。保留假设、实测和现场意见的来源差异。缺关键事实时记录受影响对象和可做的独立工作，使用部分规格交接。
7. **正常完成**时总计用 propose_rooms 按最终规格提交建模编制草案。三个工作代理、总计、真实根分别调用 end，提交 kind=complete 与各自的明确原因。真实根完成插件交接后走新的 DSH 读闸和登记编制。分析角色每次暂时停止使用 yield；有任务却遇到故障使用 blocked；用户主动终止可输入「停止分析」。插件把提前结束尝试拉回至多两次，仍失败记录宿主中断。
8. **部分或中断**时使用 status/export 查看当前阶段和缺口。partial 产物用于给用户查看已完成对象、补证责任和下一步。实际网络、宿主或模型故障由 blocked/中断记录体现，用 retry 仅恢复当前任务，并限制次数。启动预留存在但宿主未确认时先检查真实二级会话是否产生。角色没有可靠恢复路径时先保留部分结果，然后为复跑建立新任务，避免覆盖原审查历史。

## 3. 合并后验收单

| 验收项 | 通过证据 |
| --- | --- |
| 原生会话谱系与隔离 | 一条 root→规划与三条规划→二级角色记录；同一会话重复绑定、伪造身份、错误父会话、跨任务 jobId 都拒绝 |
| 限定工具与抗干涉 | 七阶段在手的会话无法运行旧流水线、shell、文件写入、SW、越级委派和任意发信（`wait_agent`/`send_message`/`list_agents` 三个只读工具放行）；普通任务仍能使用原有工具 |
| 顺序与初始盲审 | 1.1 到 7.12 的 63 个步骤有顺序记录；设计在初始预审前无可提交任务 |
| 真实联网 | 记录一条与当前工程决策相关的实际查询和返回来源，核对厂家/标准/原始资料的位置、版本与适用性；假 URL、旧 job 和无密钥均无法放行 |
| 人类原话 | 提问出现于正确的真实根；确认、估计、不知道和冲突被区别；模型自己写的文本不能充当真人原话 |
| 防止无效反驳 | 空反对、未填理由和省略未关闭硬异议被拒；连续两轮重复返工结束后仍阻塞，报告可执行取证任务 |
| 变更污染 | 更改约束后从受影响最早节点重做；旧 job、旧审查与旧编制凭证拒绝使用 |
| 中断与结束 | 各 AI 有等待、阻塞、正常结束理由；超限、崩溃或用户取消保持可追溯；部分规格无法解锁建模 |
| 正常下游 | 当前任务 63 步、四角色与真实根完成理由、编制 ticket 一致；真实建模、总装、出图和原门禁正常 |
| 工厂案例 | 至少用真实陌生业务检查原始动作、接口、环境联合状态、备件互换、隐性操作、不良隔离与完整装拆。分别统计正确阻塞、达到设计深度、案例失败及证据缺口。 |

验收时应至少加入「螺钉有数量但没孔组及实例」「改载荷后仍沿用旧接头」「罩壳与线缆装好后工具进不去」「最终规格漏掉原始生产动作」四个有预期结果的反例。一次教学案例通过只说明该案例的行为，覆盖目标按文档规定的案例分母和判据另行统计。

## 4. 结果留档

保存合并提交、部署版本、配置的非保密部分、真实根与四角色会话 ID、任务 ID、规格版本、来源、输出凭证、异常记录、案例判据和通过情况。将结果按三类填写：通过、待真实证据、阻塞。需要回退时，先停止新任务的入口并保存七阶段台账，然后让旧引擎处理其原有任务。正在运行的新任务需恢复兼容插件或导出部分成果后重新立项。
