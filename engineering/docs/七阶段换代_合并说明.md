## 4. 关键设计点

### 4.1 引擎在 `init` 时被固定

```python
state["analysis_engine"] = ANALYSIS_ENGINE        # seven_v03，服务端决定
_ensure_seven_stage_root(state)                   # seven_stage_root_session_id
```

- 模型没有参数能改它，也没有命令行开关；
- 旧任务（升级前建立）保持它们已记录的引擎，需用旧版本工具链收尾；
- 宿主没注入 `DSH_SESSION_ID` → `seven_stage_blocked` 显式记录，不静默。

### 4.2 凭证只能从宿主写的状态文件读

`seven_stage_gate.read_design()` 的判据（**一条都不能放宽**）：

1. `schema` / `taskId` / `root` / `specHash` 全对；
2. `phase == ready`，且没有待答问题、待办 job、失败角色、未解释的 facts；
3. 63 个小步**按序齐全**；
4. 每步都有本版本的知识（含真实联网来源）+ 设计 + 复审三件套；
5. 末步复审必须 `pass`；
6. 四个角色是**四个不同的真实会话**，各自登记了 `kind=complete` 的理由；
7. 房间草案属于当前 `revision`；
8. 与已保存 `ticket` 一致（不一致 = 用户改答过，必须重登记）。

### 4.3 放行路径全部复核

| 入口 | 复核点 |
|---|---|
| `workflow_gate.select` | 引擎 + 根会话 + 凭证 + ticket + 编制 + 未清澄清 |
| `mode_gate.room-start` | `recheck_design`（不允许绕过 select 开工） |
| `sw_bridge.run`（多零件前置） | 指向七阶段流程，拒绝直接建模 |
| `mode2_flow.pre-delivery` | 凭证 + ticket + 监控器 `verify-task` + docx |

### 4.4 状态目录口径**逐字一致**

| 侧 | 解析顺序 |
|---|---|
| Node | `config.stateDir` → `DSH_SEVEN_STAGE_STATE_DIR` → `dirname(workflowFile)/seven_stage` |
| Python | `DSH_SEVEN_STAGE_STATE_DIR` → `dirname(_store.state_path('workflow_state.json'))/seven_stage` |

> 这两条必须指向同一目录。历史上"同一份状态被两套路径劈成两半"踩过多次，
> 所以回归测试直接断言**两个字符串相等**。

### 4.5 联网搜索（**2026-11-18 改为外包给传话员**）

用户口径（两次，按时间顺序）：

1. 「到时候直接调用 DSH 内部的联网搜索，是可以搜索的」
2. 「bug1 是改成由那个外部插件去发布指令让去调用 DSH 的插件去，将联网搜索外包出去，
   然后去给 DSH 联网搜索了之后，再返回回插件」
   「不能打破插件现有的大脑和传话员角色的绝对地位」

**最终架构：插件自己不联网，也不需要任何搜索 key。**

```
知识(knowledge) ──action=search──► 插件落盘「检索工单」job.searchOrder
                                        （不碰网络、不读 env）
真实主对话(root/传话员) ──读 status.search.order──► 调宿主内置 web_search 实际检索
真实主对话(root/传话员) ──action=search_fill──► 插件收下来源→job.searches
知识(knowledge) ──submit──► 按来源 ID 写依据 / 出处 / 边界 / 缺口
```

三条红线：

| # | 红线 | 强制点 |
|---|---|---|
| 1 | 插件进程内**绝不**发起网络请求 | `lib/index.js` 里已删除 `braveSearch` / `hostSearch` / `webSearch`，代码里搜不到 `fetch` |
| 2 | 只有 `root` 能 `search_fill`；`knowledge` 只能发工单 | `flow.fillSearch` 抛 `SEARCH_FILL_RELAY_ONLY` |
| 3 | 传话员只搬运，不能改查询词或替知识下结论 | `SEARCH_QUERY_MISMATCH`（回填 query 必须与工单原文一致） |

为什么不让知识自己填：若允许「检索者自己出证据」，七阶段赖以成立的
**知识 → 设计 → 独立复审**三件套会直接失效。

旧的 `DSH_SEVEN_STAGE_SEARCH_URL` / `DSH_SEVEN_STAGE_BRAVE_KEY` **已废弃**，
设置它们不再有任何效果（留着只会误导部署方，见 `fixes-20261118-seven-stage-bugs.md`）。

```powershell

.\sync-to-dsh.ps1 -Prune                # 实际同步（复制 + 删除孤儿）
```

> ⚠️ **`-Prune` 是本次新增的，必须带。** 原脚本只做复制、从不删文件 ——
> 仓库里删掉的 8 个十阶段测试会一直留在安装副本里，继续 import 已经不存在的
> API（`analyst_bind` / `begin_stage` …），跑一次就报一串失败，看着像「换代失败」。
>
> 剪枝白名单**只认源码后缀**（`.py/.js/.mjs/.cjs/.ts/.md/.yml/.yaml/.ps1/.sh` …），
> 并且显式排掉 `compaction_facts/`、`trace/`、`sw_monitor/`、`reports/`、
> `seven_stage/` 等数据目录。原因是安装副本里的 `.json` 大多是**活数据**
> （`mode2_plan.json`、`sw_monitor.json`、`compaction_engine.json`、
> `artifacts_registry.*.json`、`compaction_history*.jsonl` …），
> 误删会毁掉进行中的任务；反过来「多留一个过期 .json」是无害的（所有读者都校验 schema）。
> **剪代码，不剪数据。** 被剪掉的文件都会先备份成 `.bak-prune-<时间戳>`。

## 5.3 事故复盘：`duplicate exact route "/dsh-engineering-ui/agents"`

### 现象

第一次重启后工程模式打不开：

```
webserver: duplicate exact route "/dsh-engineering-ui/agents"
```

### 根因（不在 UI 插件，在我新加的那一行）

`preset-engineering.patch.yml` 里 `engineering-seven-stage` 的配置写成了：

```yaml
stateDir: !!js process.env.DSH_SEVEN_STAGE_STATE_DIR || ''
workflowFile: !!js process.env.DSH_SEVEN_STAGE_WORKFLOW_FILE || ''
```

环境变量没设 → 传进来的是**空串** → 插件的 `install()` 抛
`SET_ABSOLUTE_SEVEN_STAGE_PATHS` →

```
preset 组合挂载失败
  → 宿主重建组合
    → 已经 apply 过的 dsh-engineering-ui 被【第二次】apply
      → ctx.webServer.register(PREFIX + '/agents') 撞上精确路由重名
```

也就是说：**一个可选的分析插件没配置，把整个工程模式连坐了。**
另外 `??` 运算符挡不住空串（只挡 `null`/`undefined`），这层"看似配了"的假象掩盖了问题。

### 修复（两道，缺一不可）

**① 插件改成"零配置也能完整加载"** —— `resolveWorkflowFile()` 按顺序探测：

| 顺序 | 来源 |
|---|---|
| ① | `config.workflowFile` / `DSH_SEVEN_STAGE_WORKFLOW_FILE`（显式指定） |
| ② | `DSH_STATE_DIR/workflow_state.json`（宿主注入的权威状态目录） |
| ③ | `<DSH_HOME>/.agent-presets/engineering/tools/workflow_state.json` |
| ④ | `<USERPROFILE>/.dsh/...`（DSH_HOME 没注入时） |
| ⑤ | `os.homedir()/.dsh/...`（环境被清理时的最后兜底） |

> ⚠️ **不按"文件是否存在"重排候选**。踩过：显式注入的 `DSH_STATE_DIR` 指向一个
> 还没 init 过的目录，而 `~/.dsh/...` 下恰好有上一次任务留下的 `workflow_state.json`；
> 一旦按存在性挑，就会挑到**别人那次任务**的状态文件 —— Node 写 A 目录、Python 读 B 目录，
> 凭证永远对不上。**显式注入永远第一优先。**

而且空串一律按"未配置"处理（`nonEmpty()`），不再让 `''` 冒充有效值。

**② 装不上时也不抛异常**（双保险）：宿主契约不全等情况走
`installDisabled()` —— 只登记一个"永远返回可操作错误"的工具，
**不注册任何 guard / 钩子 / 路由**，因此绝不会连累 preset 里其它插件。

### 现在的实际行为

| 场景 | 结果 |
|---|---|
| 零配置 | **LIVE**（注册工具 + 1 个 tool guard + 4 个钩子） |
| 只设 `DSH_HOME` / `USERPROFILE` / `DSH_STATE_DIR` / 显式 workflowFile | 全部 **LIVE** |
| 宿主契约不全（缺 subagents 等） | 降级：工具在、返回 `SEVEN_STAGE_NOT_CONFIGURED`，不动别人的路由 |

### 锁死它的回归

`test_regression_seven_stage_wiring.py` 新增 **F2 段（10 项）**：

- 零配置 `install()` **不抛异常**（直指本次事故根因）；
- 零配置仍**完整挂载**（tool guard = 1、钩子 = 4）；
- 宿主契约不全时**降级但不抛**，且不装 guard / 钩子；
- Node 与 Python 解析出的 `workflowFile` / `stateDir` **逐字相等**。

   返回体已经是七阶段证据，不再是十阶段进度。
